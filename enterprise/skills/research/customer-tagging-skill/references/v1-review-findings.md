# v1.0 → v2.0 审查发现与设计校正记录

> 背景：v1.0 为一套把 B2C 电商打标签框架直接套在 B2B 分销画像上的提示词。2026-08-20 经 TRIAD 双 Agent 独立审查（researcher 逻辑/风控视角 + writer-zh 执行者/使用者视角）+ 用户三轮设计校正后重构为 v2.0。审查方法本身：LITE 轻量分派（视角A=逻辑结构/评分体系→researcher，视角B=执行可用性/表达→writer-zh），双 Agent 交叉验证，总监裁决。

## 二、A/B 级问题摘要（值得记住的设计约束）

- MECE 重叠 5 组无归位规则 → 归位原则：**原始观测归 D3/D1，衍生分层归 D4/D5**；D3.1 只留非 RFM 字段。
- 完整性分母被 B2C 维度污染且无权重 → 双层化+加权（D0/D2 ×1.5，D1/D4 ×1.0，D3/D5 ×0.5，权重和 24）。
- 品类/品牌取值未对齐授权词表（画像写"MOSFET"，c 表词表是"功率器件"）→ 词表对齐 + dict_alias 记原文词 + OTHER 兜底。
- 准确度评分区间过宽（89 vs 60 差 29 分）→ 5 档锚点法。
- 第4级"互斥且穷尽"不现实（0402 与 BGA 混装）→ 受控词表 + OTHER。
- 穷举式提取导致输出爆炸（单客户 80-150 条）→ "穷举检查、精选输出"，单对象 ≤40 条。
- JSON 示例非法（// 注释、伪枚举"ENUM | NUMERIC"）→ 合法 JSON Schema 示例。
- 执行流程无退出条件死循环 → 退出条件：≤2 轮补充、无信息降级交付。

## 三、用户三轮设计校正（系统资产哲学，违反即回退到错误设计）

### 校正 1：跨对象标签索引表 = 全库唯一资产（不是每次任务的产物）
- 错误写法："多对象输入时，追加一份跨对象标签索引表"（带日期、随任务生成）
- 用户原则：整个数据库只应该有一份完整的跨对象标签索引表，在执行任务的过程中不断被完善。
- 修复：固定名、不带日期、增量 upsert（已有对象更新行、新对象追加行）。

### 校正 2：统一 JSON 标签库（不是每对象一份）
- 错误写法："每对象一份结构化 JSON 标签库"
- 用户原则：整个系统应该只有一份统一的标签库。
- 修复：`客户标签库.json` 固定名不带日期，objects[] 按 object_id upsert，版本自持。

### 校正 3：统一标签库取代跨对象索引表（彻底删除索引表）
- 用户原则：统一标签库本身就是跨对象结构（objects[]），加上规则层后一份文件承载"规则+数据"双重职责——跨对象索引表是冗余。
- 最终架构"一文一库"：
  - MD 报告（一次性、每对象、带日期）＝人工阅读产物
  - `客户标签库.json`（全库唯一、固定名、无日期）＝规则层 schema + 数据层 objects[] 一体

### 校正 3 后的完整闭环
```
打标签任务
  ├─ Step 1  读标签库 schema 规则层 → 按既有规则打标签
  ├─ Step 8  生成 MD 报告（一次性）
  ├─ Step 10 ① upsert 对象数据 → 标签库 objects[]
  │          ② Schema 演进检查：检测新维度 → 判断（特例 OTHER / 可推广入库）
  │          ③ 更新 schema + 版本号 vX.Y + changelog
  └─ 下游消费：直接读客户标签库.json，无需再汇总
```

## 四、Schema 演进判断依据（避免演进失控）

新维度入库前必须过判断关：**多对象通用性 / 撮合价值 / 下游消费方（产品线匹配、客户群分析）确实需要**。个别特例 → 标 OTHER 暂存不入库。新品类/新品牌超出授权词表 → 提数据资产更新建议（不擅改 authorized-product-line-reference）。

## 五、审查方法备注（本技能如何被审查）

- 分派：researcher=逻辑/结构/评分体系审查；writer-zh=执行者视角/表达/可交付性审查。双 Agent 独立发现同一问题（如评分双轨）= 高置信信号。
- 冲突裁决：writer-zh 字节级核验推翻了总监分派任务中的一个前提（表格格式）——审查任务中允许视角适度重叠，交叉覆盖反而验证可靠性。
- 输出：37 条问题（5S+10A+6B 级整合），v2.0 重构交付。
